Why use indexing for sorting if we have sort()?
While the sort() function does arrange data for you, it operates directly on the queried results. Without an index, MongoDB has to scan the entire collection and sort it, which can be slow for large datasets. Indexes come into play here by maintaining data in a pre-sorted order, allowing the database to fetch the sorted results almost instantly. This reduces computational overhead significantly compared to relying solely on sort().

......> Sort operations that use an index often have better performance than blocking sorts.

...> Indexes support efficient execution of queries in MongoDB. Without indexes, MongoDB must scan every document in a collection to return query results.

...> If an appropriate index exists for a query, MongoDB can use the index to limit the number of documents it must inspect.

...> If your application is repeatedly running queries on the same fields, you can create an index on those fields to improve performance.

...> Indexes are special data structures that store a small portion of the collection's data set in an easy-to-traverse form. 

..> MongoDB defines indexes at the collection level and supports indexes on any field or sub-field of the documents in a MongoDB collection.


....> MongoDB creates a unique index on the _id field during the creation of a collection. The _id index prevents clients from inserting two documents with the same value for the _id field. You cannot drop this index on the _id field.

...> You cannot rename an index once created. Instead, you must drop and re-create the index with a new name.

...> 

Why does performance decrease with too many indexes?
...> Each index occupies storage space and needs to be updated whenever you modify or insert new data in the collection. When you have many indexes, these updates become resource-intensive, slowing down write operations (like insert, update, or delete). Additionally, excessive indexes can increase memory usage, potentially straining the system.

When an index is created in a database, it doesn’t save the complete sorted data of the original collection. Instead, it stores only the values of the indexed field(s) in a sorted structure, such as a B-tree or a hash table, depending on the database system. This structure includes pointers (or references) to the actual records in the original collection.

Here’s what happens exactly:

Sorting and Storage of Index Field: The database organizes the values of the indexed field(s) in a sorted or hashed format, depending on the index type. These values act as keys.

Reference to Original Collection: Each key (value of the index field) in the index structure points to the corresponding record in the original collection, allowing for faster lookups.

Query Optimization: When a query is executed that involves the indexed field(s), the database uses the index to directly locate the relevant records instead of scanning the entire collection, significantly improving performance.

Indexes enhance query speed but come with trade-offs, such as additional storage requirements for the index and potential slowdowns during data modifications (insert, update, delete), as the index also needs to be updated.

How Indexing Works in MongoDB
What It Stores:

The values of the indexed field(s), stored in a sorted order.

Pointers (or references) to the actual documents in the collection.

How It Refers to the Original Collection:

Each indexed value is associated with a pointer to the corresponding document's location in the collection. MongoDB uses these pointers to fetch the original documents when needed.

Indexes are very useful for optimizing queries, but keep in mind that they come with some trade-offs, such as additional storage requirements and the need to update the index during write operations (insert, update, delete).


When you modify a document in MongoDB (be it inserting, updating, or deleting), you do not have to manually update the index. MongoDB automatically handles the index updates for you. This means:

Inserting a New Document: If you add a new document to the collection, any indexed fields in that document will automatically be added to the index.

Updating an Indexed Field: If you update the value of an indexed field in an existing document, MongoDB will modify the index to reflect the new value.

Deleting a Document: When you delete a document, MongoDB will also remove its corresponding entry from the index.

So, there is no need for you to manually manage the index. However, do keep the following in mind:

Trade-offs: Indexes come with storage overhead and can slow down write operations slightly since MongoDB has to update the index with every write (insert, update, delete).

Index Maintenance: While MongoDB does the heavy lifting, you should periodically review and optimize your indexes to ensure they're still relevant and efficient for your queries.

COMPOUND INDEXING:
-------------------- >


...> Compound indexes collect and sort data from two or more fields in each document in a collection. Data is grouped by the first field in the index and then by each subsequent field.


NOTE:
*********
...> The order of the indexed fields impacts the effectiveness of a compound index.
...>  Compound indexes contain references to documents according to the order of the fields in the index.
...> A single compound index can contain up to 32 fields.

...> Index Prefixes { The only FIRST FILED WHEN CREATING THE INDEX IS called the index prefix }.

.> Index prefixes are the beginning subsets of indexed fields. 
.> Compound indexes support queries on all fields included in the index prefix.




What are Index Prefixes? Indexes in databases help speed up searches. When we talk about index prefixes, we're referring to the beginning sections (or subsets) of fields in a compound index. A compound index is made up of multiple fields.

For example, consider the compound index: { "item": 1, "location": 1, "stock": 1 } Here, we have three fields: item, location, and stock.

An index prefix is formed by the beginning portion of these fields:

{ "item": 1 } (just the first field)

{ "item": 1, "location": 1 } (the first two fields)

How MongoDB uses Index Prefixes MongoDB is smart—it can use the compound index to run queries on the fields that match the index prefixes. So, with the example index above, MongoDB can efficiently handle queries that include:

Only item

Both item and location

All three fields: item, location, and stock

What happens if a query skips an index prefix? Indexes are ordered, meaning they follow a strict sequence. If you skip the first field (item in this case), MongoDB won't be able to use the compound index effectively for your query. For example:

Queries on location or stock alone won’t work with this compound index because they don’t include the prefix field item.

Queries on location and stock also won’t work because the prefix (item) is missing.

Special Case: Queries on Non-Consecutive Fields Let's say you want to query item and stock. MongoDB can use the index for this query because it includes the prefix (item). However, it won’t be able to optimize for the stock field since it comes after location, which is skipped.

Tip: Remove Redundant Indexes If you have both a compound index (e.g., { a: 1, b: 1 }) and a prefix index (e.g., { a: 1 }), MongoDB can already use the compound index in the same situations as the prefix index. So, unless your prefix index has special constraints (like sparse or unique rules), you can remove it to save space.

...> for a sort operation to use an index, the fields specified in the sort must appear in the same order that they appear in an index. 

NOTE: In compound index , the order of the fields and their functionality must same in the sort functions and also in the index for better performance.

Yes, you can create different types of indexes on a single collection in most modern databases, such as MongoDB or similar NoSQL databases. Here's how it works for the mentioned index types:

Single Field Index: You can create an index on a single field, such as a String, Number, or any other type of field in your collection. For example, indexing a name field will make searches on this field much faster.

Compound Index: This is an index on multiple fields in the collection. It's useful when you frequently query using a combination of fields, such as name and price. The order of the fields matters, so design the compound index based on your most frequent query patterns.

Multikey Index: When you have fields that store arrays, a multikey index automatically indexes each element of the array, allowing efficient querying of array values. For example, if your document includes an array of tags, a multikey index can be created for that array.

Hashed Index: You can use hashed indexes on fields that have a high level of uniqueness and are used for equality queries. For instance, this could be beneficial for fields like _id or other unique identifiers.

Wildcard Index: If your collection has fields with dynamic or varying names, you can use wildcard indexes to index all fields or a subset of fields dynamically.

Key Considerations
Index Limitations: Be mindful of the number of indexes you create, as excessive indexing can lead to performance overhead on write operations.

Index Design: Understand your query patterns before designing indexes. Tailor the types of indexes to optimize the performance of the most common queries.

Nested Fields: For fields within embedded or nested documents, you can create indexes using dot notation. For example you might index address.city.



TEXT INDEX :
---------------- >

Text Indexes on Self-Managed Deployments

..> Text indexes support text search queries on fields that contain string content. Text indexes improve performance when you search for specific words or strings within string content.


*****
NOTE: A collection can only have one text index, but that index may include multiple fields.

NOTE : If an existing or newly inserted document lacks a text index field (or the field is null or an empty array), MongoDB does not add a text index entry for the document.

..> 

db.<collection>.createIndex(
   {
      <field1>: "text",
      <field2>: "text",
      ...
   }
)


..> ext Index Can't Cover a Query: Text indexes in MongoDB are designed for full-text search and are only used to match specific text query operators, such as $text. They cannot cover queries that require retrieving fields other than the indexed text field. Essentially, they cannot "cover" the entire query like other index types can.


..> Sparse Property of Text Index: A sparse index in MongoDB only includes documents that contain the indexed field with a non-null value. Text indexes are always sparse by default. This means that if a field doesn't exist or has a null value in a document, that document will not be included in the text index. MongoDB automatically enforces this behavior for text indexes, even if you don't explicitly specify the sparse option while creating the index.



example of the text index:

Suppose you have a products collection, and you want to create a text index on the description field for full-text search. Here's how you can work with these points:

db.products.createIndex({ description: "text" });

db.products.insertMany([
  { name: "Laptop", description: "High performance laptop for gaming and work" },
  { name: "Keyboard", description: "Mechanical keyboard with RGB lighting" },
  { name: "Mouse", description: null },
  { name: "Monitor" }
]);



Notice that the third document has description: null, and the fourth document doesn't have a description field.

Step 2: Query Using the Text Index

db.products.find({ $text: { $search: "laptop" } });


This query uses the text index to find documents where the word "laptop" appears in the description field.

Sparse Behavior:
The text index will not include the third and fourth documents because their description field is null or doesn't exist. This demonstrates the sparse property of text indexes.


Use Cases
Documents in an online shop's clothing collection include a description field that contains a string of text describing each item. To find clothes made of silk, create a text index on the description field and run a $text query for documents with the keyword silk. The search returns all documents that mention silk in the description field.

What is a Wildcard Index?
A wildcard index is a type of database index that helps search for data in a way that allows for flexibility or patterns. Think of it as a way to quickly find something when you don’t know the exact name or value you're searching for. You use "wildcards" (special symbols like * or %) as placeholders for unknown parts of the data.

Simple Scenario to Explain
Imagine you’re organizing a library with thousands of books. All the books are listed in a catalog. Sometimes, readers don’t remember the full name of the book but may know part of the title.

For example:

One reader might say, "I want a book that starts with Harry but I can’t remember the rest."

Another reader might say, "It has the word Adventure somewhere in the title."

To help readers find these books quickly, you create Wildcard Indexes. These are special catalog entries that make it easy to look for books even if only part of the title is known.

How it Works in a Database
In databases, wildcard indexes are used to make such flexible searches faster. Without them, searching for something vague (like a part of a name) would take much longer because the database would need to look through everything one by one.

For example:

A database of names:

You have Harry Potter, Hermione Granger, Harold Smith.

If someone searches for "Har*" (meaning anything that starts with “Har”), the wildcard index allows you to instantly find all matching names: Harry, Harold, etc.

A product catalog:

You have items like Blue Shirt, Red Shirt, Blue Pants.

If someone searches for Blue*, the wildcard index quickly finds all items starting with "Blue".

Key Benefits
Speed: It’s much faster than searching without an index.

Flexibility: You can search for partial matches, like "starts with", "ends with", or "contains".







HASHED INDEXING:
-------------------- >


...> Hashed Index:

@ Hashed indexing is a way to organize and access data by using a hash function to map data to a specific location.

@ Think of it like a super-smart GPS for your data—it quickly finds where your information is stored instead of searching everywhere.


## Why is it important?
-------------------------------------->

Speed: It’s super-fast for retrieving data because the hash function directly finds the data’s “address.”

Efficiency: It works well when you have large datasets and want quick access to specific pieces of data.

Unique Key: It ensures there’s a unique location for each data point, reducing confusion.



## When to use hashed indexing:
------------------------------------ >

You have large data and need to access it frequently and quickly.

You are looking up data by a unique identifier, like customer IDs or student roll numbers.

Example: In a library system, hashed indexing can quickly find the book's details based on its unique ID.


## How does it compare to other indexes?
---------------------------------------------->

Other indexes (like sequential or binary indexing) involve searching step-by-step or dividing the search range repeatedly. Hashed indexing, on the other hand, skips all that—it directly finds the exact location using the hash function.

Example in simple terms: Imagine you have 100 lockers, and each locker has a number (1–100). Instead of searching through all the lockers to find your stuff, a hashed index is like knowing the locker number right away! If the locker number is 50, you instantly go there without checking lockers 1 through 49.


## When to use hashed indexing in MongoDB ?
----------------------------------------------->

> When you perform equality-based searches, like find({ field: value }).

*****
> Not suited for range queries like greater than or less than because hashed indexes are not ordered.

> When you create a hashed index on a field, MongoDB hashes the values of that field and stores the hashed values in the index. This makes queries that match on the hashed field fast, as MongoDB only needs to perform a hash computation on the query value to find matching documents.




..>  db.books.createIndex({author: "hashed"})

> After creating the hashed index, you can perform equality matches on the hashed field efficiently. For example:

> db.books.find({author: "F. Scott Fitzgerald" });

> It’s important to note that hashed indexes are not suitable for range queries or sort operations. 
> They are specifically designed for equality matches on fields with high cardinality. 
> Additionally, because hashed indexes store hashed values rather than the original values, you cannot directly retrieve the original values from the index.
>


> For example, a hashed index uses the same hash to store the values 2.3, 2.2, and 2.9. This is a collision, where multiple values are assigned to a single hash key.

> Collisions may negatively impact query performance.


> The hashing function does not support multi-key indexes. You cannot create a hashed index on a field that contains an array or insert an array into a hashed indexed field.

> You cannot specify a unique constraint on a hashed index. Instead, you can create an additional non-hashed index with the unique constraint.

> Hashed indexes collect and store hashes of the values of the indexed field.
